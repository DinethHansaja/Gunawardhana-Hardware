# Security

Never expose Supabase service-role keys in browser code or commit `.env.local`. Verify roles server-side from Supabase-backed identity and enforce them again with PostgreSQL RLS and restricted transaction functions. UI visibility is not an authorization boundary.

The database migrations enable RLS, separate cost fields from cashier-readable catalog data, remove broad table grants, and do not grant direct browser writes. Username-to-Auth lookup and employee provisioning/reset/deletion use a server-only Supabase secret plus Admin-checked database RPCs. Passwords are sent directly to Supabase Auth, which stores salted bcrypt hashes; password values are excluded from app tables, audit metadata, source code, and migrations. The secret key must never be prefixed `NEXT_PUBLIC_` or committed. Authentication uses Supabase's cookie SSR package and verified server-side user identity. SQL execution and role/RLS tests against the deployed project are still outstanding, as are backups/restore testing and remaining operational workflows.
